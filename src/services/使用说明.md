# Alova使用技巧

## 新的token刷新方案
更新token的方案：
1. 登录成功后，登录接口（A）会返回两个token：accessToken(时效：1个小时)和refreshToken（未知：大概是2-3小时，后端尚不清楚），两个token都存放在cookie。
2. accessToken过期后，调用任何一个业务接口，都会返回2002，这个时候会进去全局拦截器，请求刷新token（接口B）。入参是：refreshToken
3. 如果入参refreshToken未过期，会返回一对新的token：accessToken(时效：1个小时)和refreshToken（未知：大概是2-3小时）
4. 如果入参refreshToken已过期，会清空所有登录信息，退出到登录页。

## 接口的返回数据的固定结构
讨论返回数据的结构，首先我们要统一以下概念：
1. 接口成功，http状态码是200。那么当前接口已经进入了后端业务逻辑阶段，那么后端会根据业务逻辑返回一个固定结构的json（{code, message, result}）来区分：业务的成功和失败。
2. 接口失败，http状态不等于200，那么当前接口可能处于其他状况，例如404（URL不对）、5xx(服务器奔溃)等等，这种状态其实还没有真正进入后端的服务，我们统一理解为：http通信成功和失败

针对上面两种情况：业务成功和业务失败、http通信成功和失败，我们统一约定固定的json结构：
```ts
// Response Error http通信报错
// Business Error 业务报错
type RequestErrorType = 'Response Error' | 'Business Error' | null
interface ResponseResult<T> extends ResponseBaseResult {
        /** 请求服务是否成功 */
        isSuccess: boolean
        /** 请求服务的错误类型 */
        errorType: RequestErrorType
        /** 错误码 */
        code: RequestCode
        /** 错误信息 */
        message: string
        /** 返回的数据 */
        data: T
}
```
根据上面的接口定义，我们可以知道：
1. 当http通信状态码是200，且业务接口状态码是1001时，isSuccess = true， message是业务接口返回的成功提示message
2. 当http通信状态码是200，且业务接口状态码不是1001时，isSuccess = false，message是业务接口返回的错误提示message
3. 当http通信状态码不是200时，isSuccess = false， message是前端封装后，根据通用的状态码返回的固定的message
```ts
/** 请求不成功各种状态的错误, */
export const ERROR_STATUS = {
    default: '发生未知错误,请联系管理员!',
    400: '请求格式错误或者参数错误！',
    401: '用户没有权限（令牌、用户名、密码错误）!',
    403: '用户得到授权，但是访问是被禁止的!',
    404: '网络请求错误,URL地址错误！',
    405: '网络请求错误,请求方法未允许!',
    408: '网络请求超时',
    500: '服务器错误,请联系管理员!',
    501: '网络未实现!',
    502: '网络错误!',
    503: '服务不可用，服务器暂时过载或维护!',
    504: '网络超时,请联系管理员!',
    505: 'http版本不支持该请求!',
}
```


## 关于接口提示通用配置
> 后台管理系统，增删改查操作可能都会给予用户提示反馈，所以需要一个通用的提示配置

FitsAdmin框架的默认配置是：
1. 请求成功时，即isSuccess = true，默认不弹出提示
2. 业务请求失败、http通信失败，isSuccess = false，默认弹出错误提示，并且错误提示来源于后端接口返回message参数

如果前端需要改变默认配置，可以进行下面两种操作
### 打开成功提示的配置
```ts
// meta的接口配置
   // 自定义method的meta元属性大概有哪些参数，可拓展任意值
    interface MethodMeta {
        // 官方自带的授权角色
        authRole: string
        // 是否要加密解密
        encrypt: boolean
        // 是否打开业务错误提示，默认是true
        openErrorTips: boolean
        // 是否开启业务成功提示，默认是false，要自动开启
        openSuccessTips: boolean
    }




//根据角色ID获取用户集合
export function fetchGetRoleUserList(params: Partial<{ id: string }>) {
    const method = request.Get<Service.ResponseResult<Array<{ userID: string, userName: string }>>>('/SysRole/getRoleUserList', { params })
    method.meta = {
        // 通过method的meta属性，openSuccessTips属性是固定属性，不能随便写的。
        openSuccessTips: true
    }
    return method
}
```

### 关闭错误提示的配置
```ts
 export function fetchGetRoleUserList(params: Partial<{ id: string }>) {
    const method = request.Get<Service.ResponseResult<Array<{ userID: string, userName: string }>>>('/SysRole/getRoleUserList', { params })
    method.meta = {
        // 通过method的meta属性类似router里面的元数据，可拓展很多自定义属性
        openErrorTips: false
    }
    return method
}  
```


## 理解Method和UseRequest Hook的区别
- Method是Alova的请求方法的实例，每个 method 实例描述了每个请求的类型、请求 url、请求头、请求参数等，类似axios.get(url[, config])、axios.post(config)。
- UseRequest Hook是Alova的请求钩子，它可以在请求发送之前和之后执行自定义逻辑，并且控制各种接口的状态。类似axios.request(config)


alova 提供的useRequest在正常情况只会发送一次请求，并获取响应数据，那为什么不直接使用 method 实例来发送请求呢？

这是因为useRequest可以帮我们自动管理loading、data、error、onsuccess等可以直接使用的响应式ref数据，

因此，如果你需要使用这些状态时，使用useRequest不需要自行维护数据。但相反，你并不需要在整个项目中只适用useRequest，例如在只关心获取信息，而不需要使用到loading、error等的时候，在组件外获取数据的时候，可以使用 method 实例来发送请求

## Method和UseRequest Hook的具体使用场景
根据我在系统设置-角色管理模块的实践，我总结了一下几种应用场景：
1. 简单的操作请求可以直接用method 实例来发送请求，例如：删除操作、是否有默认权限、是否关联用户。
   简单来说，就是你可以看接口返回的数据，如果接口设计中，没有返回很多参数或者是返回只有true or false这种操作性的接口，类似于删除接口，就是使用method就行了。因为这种接口就是一种非常具体操作接口，根据某个id直接操作数据库，对后端性能要求很低，接口响应非常快，不需要很多状态类似loading这种状态判断。
2. 列表接口查询， 下拉选择数据源接口、各种表单提交的接口、详情查询的接口，类似这种复杂的接口就需要使用useRequest进行各种状态的控制了。

## useRequest中 onSuccess 和 send 的具体使用技巧
>  onSuccess是成功回调的设置函数，返回的数据结构是：AlovaSuccessEvent

### onSuccess

####  AlovaSuccessEvent
| Name      | Description                                                                              | Type    | Version |
| --------- | ---------------------------------------------------------------------------------------- | ------- | ------- |
| method    | 当前请求的 method 对象	                                                 | Method  | -       |
| sendArgs  | 响应处理回调的参数，该参数由 use hooks 的 send 传入 | any[]   | -       |
| data      | 响应数据                                                                            | any     | -       |
| fromCache | 响应数据是否来自缓存                                              | boolean | -       |

```ts
const { onSuccess } =await fetchLogin(loginData)
onSuccess(response => {
    if (response.data) {
        const { isSuccess, message, data } = response.data;
        if (isSuccess) {
            this.accessToken = data.token;
            this.refreshToken = data.refreshToken;
            resolve(true)
        } else {
            resolve(false)
        }
    }
})
```

### send
> send 函数用于手动发送请求，返回一个 Promise，该 Promise 会在请求完成时 resolve，可以解构出别名，特别注意它的返回数据格式，于onSuccess的返回数据格式不一致，它是直接返回`Service.ResponseResult`我们定义的数据结构
```ts
// 获取角色的列表
const { send: GetRoleList, loading: listLoading } = fetchRoleList();
// 保存角色
const { send: GetDepartmentSource, loading: saveLoading } = fetchSaveRole();

// 第一种使用方式，可以在任何一个地方调用，跟旧的http方案使用方法差不多，唯一的区别就是返回结构不一样，需要微调
 GetRoleList(requestData).then(response => {
    const { isSuccess, data: result } = response;
    if (isSuccess) {
       // something code
    } 
})

// 第二种使用方式，更加简洁，逐行模式，强烈推荐
const { isSuccess, data } = await GetDepartmentSource({ scene: 1 });
if (isSuccess) {
    let arr = XEUtils.toTreeArray(data)
    treeData.value = XEUtils.toArrayTree(arr, { parentKey: "parentID" })
}

```

## 关于loading中间件的具体使用场景
> loading中间件的目的是为了在请求过程中，在页面上显示loading效果，以提升用户体验。

主要分为两个loading，全局loading和局部loading
1. 全局loading的中间件：delayLoadingMiddleware，通过函数式`ElLoading`服务产生
2. 局部loading的中间件：delayDirectiveLoadingMiddleware，通过`v-loading`指令产生

为了更好的交互体验，尽可能使用局部loading，全局loading只有在请求时间较长时才使用，比如请求接口需要10秒以上，才使用全局loading，否则使用局部loading，前端开发者要有合理的判断。
如果要使用loading的接口，统一用`useRequest`Hook的模式，它能给你带来`loading`变量的控制，不需要你每个页面都要写一次变量，如果一个页面有多个模块的loading，可以对loading变量设置别名。

这里有一点要注意的是，它跟fitadmin框架的封装的Fitstable组件不能共用，因为vxetable的loading已经做好了封装，vxetable开启代理模式的时候，它已经统一了loading的显示和隐藏，所以fitadmin框架的封装的Fitstable组件和v-loading不能同时使用。

## 请求的并行方案
> 接口的并行是指，同一时间同时发起多个接口请求，我们遇到场景更多是在仪表盘中，每个图表都需要请求一个接口或者多个接口获取图表的数据源，这种就是并行请求了。我们曾经遇到的坑是，同时发起5个以上的接口，所有的接口状态都为pending，导致页面卡死。
简单的并行请求，只需要同时调用多个 useRequest 即可。
```ts
const { data: todoList } = useRequest(todoListGetter);
const { data: todoCounter } = useRequest(todoCountGetter);
```
但这样的请求只适用于单纯的并行请求，如果你需要在并行请求都完成后再进行某些操作，有以下两种方式可以实现：

### 方案一：
手动创建 promise 对象，并使用Promise.all完成效果。
```ts
const { onSuccess: onListSuccess} = useRequest(todoListGetter);
const {onSuccess: onCountSuccess, onError: onCountError } = useRequest(todoCountGetter);

// 手动创建promise对象
const listPromise = new Promise((resolve, reject) => {
  onListSuccess(resolve);
});
const countPromise = new Promise((resolve, reject) => {
  onCountSuccess(resolve);
  // onCountError可以不需要监听，onError函数的触发是当onSuccess里面有报错，才会触发
  onCountError(reject);
});
const [listEvent, countEvent] = await Promise.all([listPromise, countPromise]);
// 并行请求完成，继续处理业务...
```

### 方案二：
使用useRequest函数返回的send函数，调用send将会返回一个可用的 promise 对象。
```ts
// 先让它们不自动发送请求
const { send: sendList } = useRequest(todoListGetter, { immediate: false });
const { send: sendCount } = useRequest(todoCountGetter, { immediate: false });

// 利用send函数返回的promise对象
const parallelRequest = async () => {
  const [listResponse, countResponse] = await Promise.all([sendList(), sendCount()]);
  // 并行请求完成，继续处理业务...
};
```


## 请求的串行方案
> 串行请求是指在进行多个网络请求时，每个请求必须等待前一个请求完成（无论成功或失败）之后，才能开始下一个请求的过程。这种方式确保了请求的执行顺序，即每个请求依次进行，不会同时发出多个请求

使用 `useRequest` 或者 `useSerialRequest`  执行串行请求， 有三种方式

### 方案一：


让第一个请求自动发出，第二个请求在第一个请求的onSuccess回调中触发，即可完成串行请求，可通过以下写法完成串行请求：

```ts
//
const { onSuccess } = useRequest(todoListGetter);
const {  send: sendTodoDetail } = useRequest(todoId => todoDetailGetter(todoId), { immediate: false });

// 先获取列表，再获取第一个todo的详情
onSuccess(event => {
  sendTodoDetail(event.data.todoList[0].id);
});
```

### 方案二：

使用useRequest函数返回的send函数，调用send将会返回一个可用的 promise 对象。

```ts
// 先让它们不自动发送请求
const { send: sendList } = useRequest(todoListGetter, { immediate: false });
const { send: sendTodoDetail } = useRequest(todoId => todoDetailGetter(todoId), { immediate: false });

// 利用send函数返回的promise对象
const serialRequest = async () => {
  const {isSuccess, data} = await sendList();
  if (isSuccess) {
      const todoDetail = await sendTodoDetail(data.todoList[0].id);
      // 串行请求完成，继续处理业务...
  }
};
```

### 方案三：
使用useSerialRequest函数返回的send函数，调用send将会返回一个可用的 promise 对象。这个方法相对复杂很多，可能前端开发处理起来不太容易，容易犯错，暂时没发现这个方法能带来很大的好处，先记录出来，后面摸索用这个hook的实际场景，再总结出来。

```ts
// 接口1，调用的method实例
const { send: sendList } = useRequest1()
const { send: sendTodoDetail } = useRequest2()

const {send: allSend } = useSerialRequest([
    (params: Partial<{ id: string }>) => sendList(params),
    (response1, params: Partial<{ id: string }>) => {
        return sendTodoDetail(response1.todoList[0].id)
    }
], {
    immediate: false
});

// 调用useSerialRequest提供的send方法，allSend方法是决定了两个接口的调用时机
const {data} = await allSend({ id: '1' })
// 这里的data结果是接口2：sendTodoDetail具体返回结果，接口1：sendList的返回结果，已经在response1的参数里面了
```
